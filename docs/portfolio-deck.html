오래 걸리던 다운로드를,
추적할 수 있는 작업으로

300~400건

현장 엔지니어(CE) 증빙 첨부파일을 한 요청에서 모아 압축하던 다운로드

Full Stack · Vue · Spring Boot · MyBatis · Hazelcast

문제

첨부파일 300~400건을 한 번에 압축하면 요청이 오래 멈춰 있었고, 사용자는 진행 중인지 실패했는지 알 수 없었습니다.

판단

화면 요청과 압축 실행을 나누고, 작업 ID 하나로 서버 상태와 화면을 이어 주기로 했습니다.

구현
  • 전용 실행기에서 압축하고 대기, 진행, 완료, 실패 상태를 저장했습니다.
  • Vue 화면이 2초마다 상태를 조회하고, 새로고침 뒤에도 기존 작업을 찾아 이어서 보여 줍니다.
  • 완료 파일은 스트리밍으로 내려받고, 만료된 결과 파일은 자동으로 지웁니다.
결과

300~400건 규모의 대량 다운로드를 비동기 작업으로 운영하고 있습니다. 사용자는 진행 상황과 실패 여부를 보고 완료 파일을 이어서 내려받습니다.

경계 조건을 고정한 단위 테스트

Backend · Java 21 · Spring Boot · Hazelcast

문제

비밀번호 초기화 인증번호가 알림톡으로 나가는데, 반복 클릭이나 자동화된 요청을 막는 장치가 없었습니다. 서버별 메모리로 제한하면 요청이 나뉘어 들어올 때 제한이 먹히지 않을 수 있었습니다.

판단

이미 쓰고 있던 분산 맵에 TTL 쿨다운을 두고, 동시에 들어온 요청 중 한 건만 통과하도록 원자적 획득 연산을 쓰기로 했습니다.

구현
  • putIfAbsent로 쿨다운을 원자적으로 잡고, 만료 항목은 조건부 삭제로 지웠습니다.
  • 제한 키는 계정과 전화번호를 SHA-256 해시로 만들어 원문이 남지 않게 했습니다.
  • 화면에는 남은 대기 시간을 돌려줘 언제 다시 시도할지 알려 줍니다.
결과

어느 서버로 요청해도 같은 제한이 걸리고, 사용자는 남은 대기 시간을 안내받습니다.

교육용 단말 운영 시스템(TSMS) · 조회 성능05 / 11

60초 안에 끝나지 않던 통합 뷰 조회 재작성

60s→63~69ms

운영 DB에서 같은 결과를 돌려준 시간

2026.09, 이력이 가장 많은 고객 기준

870배 이상

기존 쿼리 대비 최소 단축 폭

2.1조→1,854행

실행계획의 추정 행 수

문제

A/S 이력과 정산 세부현황 조회가 여러 테이블을 합친 통합 뷰를 거치면서, 데이터가 쌓일수록 화면이 수십 초씩 기다렸습니다.

제약

화면의 조회 조건과 표시 항목은 그대로 둬야 했고, 같은 뷰를 쓰는 다른 화면에 영향을 주면 안 됐습니다.

판단

고객 조건이 뷰 안까지 전달되지 않아 뷰 전체를 만든 뒤 거르고 있었습니다. 인덱스를 더하는 대신 화면이 쓰는 컬럼만 기본 테이블 조인으로 다시 썼습니다.

구현

통합 뷰 대신 기본 테이블을 직접 조인해 고객 조건이 처음부터 인덱스를 타게 하고, 화면이 쓰는 컬럼만 남긴 채 최신 처리 이력은 서브쿼리로 붙였습니다.

검증

바꾸기 전후 쿼리를 같은 파라미터로 실행해 결과 행이 일치하는지 비교했습니다.
