B2B Partner Portal (PPS)

Feb 2025 – Present

Live · from initial build through features, acceptance, deployment and operations

A portal where headquarters and about 500 partner companies handle partner registration and contracts, plus training, certification, documentation and evaluation for 824 field-engineer (CE) accounts.

  • Zipping 300–400 attachments became a job with visible progress — Split the zip out of the request into a job-ID based async job. The screen shows waiting / running / done / failed; state lives in a Hazelcast distributed map, so both servers report the same progress and the download resumes after a refresh.
  • Removed the cause of mislinked attachments, blocked on screen and server — A new CE could inherit the previous CE's attachment group through shared Vue state; each screen now creates fresh state, and the server rejects an attachment group already used by another CE.
  • One password-reset rate limit across two servers — Atomic acquisition on a Hazelcast distributed map lets only one of any concurrent requests send a code. Limiter keys are SHA-256 hashes, so no raw account or phone number is stored; edge cases are pinned by unit tests.
  • Headquarters account provisioning: 3 steps into one screen — Internal account, portal account and manual DB entry became one procedure; if the internal-system call fails, the portal save rolls back.
  • Notification sends: 5 send points into one shared service — Recipients and send conditions are managed in the DB, so a policy change is a configuration update, not a code change.
  • Automated deployment — Checkout, build, transfer, backup and sequential deployment to two servers run as Jenkins jobs.

Sep 2025 – Present

Live · maintenance and new program features, acceptance, deployment

  • A lookup that never finished within 60 s now returns in 63–69 ms (at least ~870x) — The execution plan showed the customer filter never reached inside a consolidated view.   • Bulk registration checks behind QR codes for 108,237 devices — Serials are checked against production-intake records and prior registrations before saving, and QR codes carry a public ID instead of internal identifiers (of 111,593 devices).
  • School inspections moved on screen — 14,882 checklists at 71 schools — One flow from schedule approval to checklist, e-signature and confirmation; a version check on save keeps one inspector from overwriting another's results (Sep 2026, of 119 target schools).
  • External API keys removed from the browser on 25 screens — Map, address and education-administration calls moved to a shared server path, so an integration change is a single server-side edit.
  • Public enrollment screens for parents in 4 education offices — Consent, delivery booking and QR pickup on a phone without logging in, including deadline locks, error screens and a dark-mode QR fix.
  • Live inspection data cleaned up with a way back — Prepared backup, rollback and verification SQL first, then removed duplicate rows while keeping results and re-keyed storage to the full serial (applied Jul 2026).

ticket-rush · First-come ticketing system

Aug 2026 – in progress

Personal · public code github.com/YongjaeKwon/ticket-rush

A reservation system built test-first around one rule: the same seat is never sold twice.

  • 100 concurrent requests for one seat, 1 success — A Redis hold reserves the seat for 5 minutes, expired holds are refused at payment, and a MySQL (show, seat) primary key blocks a second confirmation.
  • Still one confirmation when Redis holds disappear — With hold keys deleted to create 10 duplicate holds confirmed at once, exactly one seat and one booking remain (Testcontainers integration test).
  • Payment retries — A retry with the same key gets the first response back; a new attempt after a decline uses a new key.
  • Web and E2E — Next.js seat map (Canvas), queue position (SSE) and payment screens with Playwright E2E in CI. Now building phase 3: relaying outbox events to Kafka.
