# 직무 관점별 문제 해결 사례 개편 설계

## 배경

현재 포트폴리오는 단일 페이지에서 `전체`, `Frontend`, `Backend` 관점을 전환하며 같은 프로젝트를 서로 다른 설명과 순서로 보여준다. 이 구조와 시각 디자인은 유지하되, 핵심 실무 프로젝트인 PPS와 TSMS가 단순 업무 나열이 아니라 문제 해결 능력을 증명하도록 표현을 개편한다.

## 목표

- PPS와 TSMS를 `문제 -> 판단 -> 구현 -> 결과` 순서로 읽히게 한다.
- Frontend 관점은 화면 흐름, 입력 검증, 상태 및 오류 안내와 API 연동을 강조한다.
- Backend 관점은 작업 분리, 데이터 검증 및 저장, 외부 연계와 배포 및 운영을 강조한다.
- 전체 관점은 화면부터 서버, 데이터, 배포까지 연결한 범위를 균형 있게 보여준다.
- 기존 단일 페이지, 직무 탭, 프로젝트 순서, 비식별화 시각 자료와 상세 모달을 유지한다.
- 확인 가능한 운영 수치만 사용하고 추정 성과나 임의의 개선율은 만들지 않는다.

## 비목표

- 별도 직무별 사이트나 라우트를 만들지 않는다.
- 새로운 프로젝트 상세 페이지를 추가하지 않는다.
- 이력서 PDF를 직무별로 분리하지 않는다.
- SSAFAST, ddoing, MODAC, quant-lab의 콘텐츠 구조를 이번 범위에서 전면 개편하지 않는다.
- 회사, 고객사, 사용자 또는 장비를 식별할 수 있는 실제 화면과 데이터를 공개하지 않는다.

## 사용자 경험

### 프로젝트 카드

현재 카드 레이아웃과 비식별화 시각 자료는 유지한다. 설명 영역은 다음 우선순위로 재구성한다.

1. 프로젝트 규모와 역할을 알 수 있는 짧은 개요
2. 해결한 핵심 문제
3. 선택한 접근 또는 판단
4. 확인 가능한 결과 또는 운영 규모

카드에는 네 단계 전체를 길게 노출하지 않는다. `문제`와 `결과`를 가장 빠르게 스캔할 수 있게 보여주고, 판단과 구현은 짧은 설명 또는 상세 모달로 연결한다.

### 프로젝트 상세 모달

PPS와 TSMS의 상세 모달은 프로젝트 개요와 직무별 담당 영역 다음에 네 단계 사례를 표시한다.

1. 문제: 기존 방식에서 발생한 사용 또는 운영상의 제약
2. 판단: 선택한 해결 방향과 그 이유
3. 구현: 실제로 담당한 화면, 서버, 데이터 또는 배포 작업
4. 결과: 운영 적용 여부와 확인 가능한 수치

`Frontend`와 `Backend` 탭에서는 해당 관점의 사례를 우선 표시한다. `전체` 탭에서는 양쪽을 연결한 대표 사례를 표시한다.

## 프로젝트별 강조 내용

### PPS Frontend

- 문제: 300~400명 규모 첨부파일 압축 중 진행, 완료, 실패 여부를 알기 어려웠다.
- 판단: 오래 걸리는 요청을 화면에서 하나의 명시적인 작업 상태 흐름으로 관리한다.
- 구현: Vue 화면에 대기, 진행, 완료, 실패 상태와 주기적 상태 조회를 연결하고 새로고침 이후 기존 작업을 다시 찾아 이어서 확인하도록 구성한다.
- 결과: 사용자가 작업 진행과 실패 여부를 확인하고 완료 파일을 이어서 다운로드할 수 있게 됐다.

### PPS Backend

- 문제: 압축 완료까지 HTTP 요청이 계속 대기하고 결과 파일 수명과 실패 상태를 관리하기 어려웠다.
- 판단: 요청 처리와 압축 실행을 분리하고 작업 ID를 중심으로 상태를 관리한다.
- 구현: 별도 실행기, 상태 저장, 완료 파일 스트리밍과 만료 파일 정리를 구현한다.
- 결과: 300~400명 규모 대량 다운로드를 비동기 작업으로 운영하며 화면에서 진행과 실패 상태를 확인할 수 있게 됐다.

### TSMS Frontend

- 문제: 종이 중심 점검 업무는 일정, 대상, 미완료와 재점검 이력이 분리되어 다음 작업을 파악하기 어려웠다.
- 판단: 현장 절차를 일정, 대상, 회차와 결과 상태로 나누고 담당자가 다음 행동을 알 수 있게 만든다.
- 구현: WebSquare 화면에서 점검 일정, 대상, 2차 및 3차 재점검, 결과 파일과 상태를 연결한다.
- 결과: 2026년 7월 기준 119개 대상 학교 중 56개 학교의 일정이 확정됐고 21개 학교, 약 3,800대의 점검이 완료됐다.

### TSMS Backend

- 문제: 중고거래 게시글 확인에 외부 사이트 접속과 반복 입력이 필요했고, 화면별 외부 연계 구현도 중복됐다.
- 판단: URL 문자열을 서버에서 규칙 기반으로 분석하고 공통 연계 기능을 단일 서버 경로로 모은다.
- 구현: 사이트별 게시글 번호 추출과 중복 검사를 구현하고 카카오 주소 검색 및 NEIS 연계를 공통화한다.
- 결과: 중고거래 모니터링 기능을 약 1주 만에 배포했고, 공통 연계 경로는 25개 화면에서 사용한다. 운영 규모는 QR 108,237대 발급과 안내 메시지 2,931건으로 확인한다.

## 데이터 구조

`FeaturedProject`와 직무별 `ProjectPerspective`에 선택적인 문제 해결 사례 데이터를 추가한다.

```ts
type CaseStudyStep = {
  problem: string;
  decision: string;
  implementation: string[];
  outcome: string[];
};
```

- PPS와 TSMS의 기본 콘텐츠 및 `frontend`, `backend` 관점에 사례 데이터를 작성한다.
- 사례 데이터가 없는 프로젝트는 현재 카드와 상세 콘텐츠를 그대로 사용한다.
- 기존 `card`, `detail`, `perspectives` 병합 방식은 유지해 중복을 최소화한다.

## 컴포넌트 변경

- `ProjectsView.vue`에서 활성 관점의 사례 데이터를 계산한다.
- 카드의 기존 `실제 운영` 영역은 문제와 결과가 한눈에 보이는 요약으로 바꾼다.
- 상세 모달에 네 단계 사례 블록을 추가하거나 기존 상세 블록을 네 단계 순서로 재구성한다.
- 새로운 컴포넌트는 반복되는 네 단계 렌더링이 충분히 복잡할 때만 분리한다.
- 현재 색상, 카드 크기, 다이어그램, 탭과 모달 동작은 유지한다.

## 예외 처리

- 사례 데이터가 없으면 기존 `card.result`, `detail.workPoints`, `detail.results`를 그대로 표시한다.
- 결과 수치의 기준 시점은 문장 안에 명시한다.
- 비공개 실무 프로젝트의 실제 화면, 고객사명과 식별 가능한 데이터는 추가하지 않는다.

## 검증

- `전체`, `Frontend`, `Backend` 탭 전환 시 PPS와 TSMS의 문제 해결 사례가 올바르게 바뀌는지 확인한다.
- 상세 모달이 키보드와 닫기 버튼으로 정상 동작하는지 확인한다.
- 데스크톱과 모바일에서 네 단계 제목과 본문이 겹치거나 잘리지 않는지 확인한다.
- 사례 데이터가 없는 공개 프로젝트가 기존 방식으로 정상 표시되는지 확인한다.
- TypeScript 검사와 프로덕션 빌드를 통과해야 한다.

## 완료 기준

- 기존 포트폴리오의 전체 구조와 시각적 인상이 유지된다.
- PPS와 TSMS 카드에서 핵심 문제와 결과를 30초 안에 파악할 수 있다.
- 상세 모달에서 문제, 판단, 구현, 결과의 순서가 명확하다.
- Frontend와 Backend 탭에서 서로 다른 직무 기여가 드러난다.
- 모든 수치는 현재 저장된 프로젝트 데이터나 확인된 운영 사실에 근거한다.
