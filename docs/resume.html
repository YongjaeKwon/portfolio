B2B 협력사 포털 (PPS)

2025.02 ~ 현재

운영 중 · 초기 구축 참여부터 기능 개발, 검수, 배포, 운영까지

본사와 약 500개 협력사가 파트너 등록 · 계약과 현장 엔지니어(CE) 계정 824개의 교육 · 자격 · 증빙 · 평가를 처리하는 포털입니다.

  • 첨부파일 300~400건 다운로드를 진행 상태가 보이는 작업으로 — 한 요청에서 압축하느라 화면이 멈추던 흐름을 작업 ID 기반 비동기 작업으로 나눴습니다. 대기 · 진행 · 완료 · 실패를 화면에 보여 주고, 상태를 Hazelcast 분산 맵에 두어 서버 2대 어디서 조회해도 같으며 새로고침 후에도 이어서 내려받습니다.
  • 첨부파일 오연결 원인 제거, 화면과 서버에서 이중으로 방어 — 새 CE를 등록할 때 직전 CE의 첨부파일 그룹이 남던 Vue 공통 상태를 인스턴스별 상태 생성으로 바꾸고, 서버는 다른 CE가 쓰는 첨부파일 그룹이면 저장을 거부하게 했습니다.
  • 서버 2대에서 똑같이 걸리는 인증번호 요청 제한 — Hazelcast 분산 맵의 원자적 획득으로 동시 요청 중 한 건만 발송되게 했습니다. 제한 키는 SHA-256 해시로 만들어 계정 · 전화번호 원문을 남기지 않고, 경계 조건은 단위 테스트로 고정했습니다.
  • 본사 계정 발급 3단계를 한 화면으로 — 사내 계정 생성, 포털 계정 생성, DB 직접 입력으로 나뉘어 누락 위험이 있던 절차를 하나로 묶고, 사내 시스템 연동이 실패하면 포털 저장도 취소되게 했습니다.
  • 알림톡 발송 지점 5곳을 공통 서비스 1곳으로 — 수신자와 발송 조건을 DB에서 관리해 정책이 바뀌어도 코드 대신 설정으로 반영합니다.
  • 배포 절차 자동화 — 소스 가져오기, 빌드, 서버 전송, 기존 파일 백업, 두 서버 순차 배포를 Jenkins 작업으로 묶었습니다.

사용 기술Vue · JavaScript · Java 21 · Spring Boot · MyBatis · MariaDB · Oracle · Hazelcast · Jenkins

교육용 단말 운영 시스템 (TSMS)

2025.09 ~ 현재

운영 중 · 유지보수와 사업별 신규 개발, 검수, 배포

서울시교육청 디벗 사업의 교육용 단말 약 11만 대를 등록부터 배송 · 설치, A/S, 점검까지 관리하는 시스템입니다. 여러 운영팀과 4개 교육청 학부모가 씁니다.

  • 60초 안에 끝나지 않던 조회를 63~69ms로 (최소 약 870배) — 실행계획을 보니 고객 조건이 통합 뷰 안까지 전달되지 않았습니다. 화면이 쓰는 컬럼만 기본 테이블 조인으로 다시 쓰고, 바꾸기 전후 결과 행이 같은지 비교했습니다(운영 DB 실측, 2026.09).
  • 교육용 단말 108,237대 QR 발급에 쓰인 대량 등록 검증 — 저장 전에 생산입고 정보와 기등록 여부를 대조하고, QR에는 내부 식별자 대신 외부 노출용 ID를 넣었습니다(전체 111,593대 중).
  • 학교 방문 점검 전산화 — 71개교 점검표 14,882건 — 일정 승인부터 점검표 · 전자서명 · 확인서까지 한 흐름으로 만들고, 저장 시점에 변경 번호를 확인해 다른 담당자의 결과를 덮어쓰지 않게 했습니다(2026.09 기준, 대상 119개교 중).
  • 25개 화면의 외부 API 키 브라우저 노출 제거 — 지도 · 주소 · 교육행정정보 호출을 서버 공통 경로로 옮겨, 연동 정보가 바뀌어도 서버 한 곳만 고치면 됩니다.
  • 4개 교육청 학부모 공개 접수 화면 — 로그인 없이 휴대폰에서 동의 · 배송 예약 · QR 배부 확인을 마치게 하고, 마감 잠금 · 오류 화면 · 다크 모드 QR 인식 문제까지 처리했습니다.
  • 운영 중인 점검 데이터 정리 — 백업 · 롤백 · 사후 검증 SQL을 먼저 준비한 뒤, 점검 결과를 보존한 채 중복 행을 정리하고 저장 기준을 전체 시리얼로 바로잡았습니다(2026.07 반영).

사용 기술WebSquare5 · JavaScript · JSP · Java 11 · Spring MVC · MyBatis · MariaDB

개인 · 코드 공개 github.com/YongjaeKwon/ticket-rush

선착순 예매에서 같은 좌석이 두 번 팔리지 않는지를 테스트로 확인하며 만드는 예매 시스템입니다.

  • 좌석 하나에 동시 요청 100건, 예매 성공은 1건 — 좌석을 Redis로 5분간 먼저 잡아 두고, 시간이 지나면 결제를 거절하며, 마지막으로 MySQL (회차, 좌석) 기본키가 두 번째 확정을 막습니다.
  • Redis 선점 정보가 사라져도 확정은 1건 — 선점 키를 지워 같은 좌석에 선점 10건을 만든 뒤 동시에 확정해도 확정 좌석과 예매가 1건씩만 남는 것을 Testcontainers 통합 테스트로 확인했습니다.
  • 결제 재시도 처리 — 같은 키로 다시 온 결제 요청에는 처음 응답을 돌려주고, 거절 뒤 새 시도는 새 키를 씁니다.
  • 웹과 E2E — Next.js로 좌석맵(Canvas) · 대기 순번(SSE) · 결제 화면을 만들고 Playwright E2E를 CI에서 돌립니다. 지금은 Outbox 이벤트를 Kafka로 넘기는 3단계를 진행하고 있습니다.

개인 · 비공개

일요일 카페에서 7명과 한 사람씩 1:1로 대화하고, 서로 선택한 경우에만 연결되는 오프라인 소개팅을 실제로 운영하려고 만들고 있는 서비스입니다.

  • 남은 자리 하나에 20명 동시 신청, 성공은 1건 — 회차 행을 먼저 잠근 뒤 성별 인원을 세고 저장합니다. 같은 회원이 8번 동시에 눌러도 신청은 1건이고, 잠금 대기는 2초로 제한해 서비스 전체가 멈추지 않게 했습니다(PostgreSQL 통합 테스트).
  • 서비스 나누기 — API Gateway 뒤에 회원 · 일정 · 매칭 · 알림 · 결제 서비스를 두고 서비스마다 자기 DB만 씁니다. Gateway가 JWT를 검증해 내부 헤더로 넘깁니다.
  • 참가자 웹 · 운영자 웹 — 가입 · 일정 보기 · 참가 신청과 회원 조회 · 회차 관리 · 신청 취소가 동작하고, 결제 · 체크인 · 매칭은 다음 단계입니다. 기능마다 설계서를 먼저 확정한 뒤 구현합니다.

사용 기술TypeScript · NestJS · Next.js · PostgreSQL · Prisma · Turborepo · Vitest · Playwright
